# Render + Aiven deployment

The application is prepared for one public Docker web service with Next, Express and nginx, backed by external MySQL. Authentication and sockets share the public hostname. This directory contains deployment assets; it is not a record that the live deployment has succeeded.

## Aiven

The owner created service `dzencode` in project `vladkruglovfencer-dbf9`. Wait for Running, then open Overview / Connection information and download its CA certificate. Keep connection passwords outside chat and version control.

1. Copy `.env.example` in this directory to `.env.local` and fill in Aiven's database host, port, database name (normally `defaultdb`), user and password.
2. Save the downloaded CA as `deploy/aiven-ca.pem` (ignored by Git).
3. Before using this migration against a database with existing data, take an export. For a new empty demo database, apply schema and initial seed with:

```bash
docker compose --env-file deploy/.env.local -f deploy/compose.yml run --rm --build migrate
```

The migration container creates a temporary Java truststore from the provider CA and uses Connector/J `VERIFY_IDENTITY`. The password is supplied in the container environment. It applies the application's changelog only, without creating/resetting a test database. Re-running applied changeSets preserves existing data. Live Aiven execution and server privileges must still be verified.

## Render

Use the committed `render.yaml` from `stage/8-deploy` after the implementation is reviewed and pushed. The service uses `deploy/Dockerfile`, repository-root build context, the Free plan and `/api/health`. Auto-deploy is off. The official Blueprint UI allows selection of the source branch. A configuration that exists only locally cannot be read by Render.

Supply the following values in the initial Blueprint environment prompts:

| Variable                                                  | Source                                                       |
| --------------------------------------------------------- | ------------------------------------------------------------ |
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` | Aiven Connection information                                 |
| `DB_SSL_CA`                                               | Complete PEM contents of the downloaded Aiven CA certificate |
| `DB_SSL`                                                  | Blueprint sets `true`                                        |
| `AUTH_COOKIE_SECURE`                                      | Blueprint sets `true`                                        |
| `AUTH_JWT_SECRET`                                         | Generated by Render; preserve it across redeploys            |

Render's `RENDER_EXTERNAL_URL` supplies the public origin at runtime. An explicit `PUBLIC_ORIGIN` overrides it for an approved custom domain. Do not append a slash or path. The runtime binds nginx to `PORT` on all interfaces; Next (3000) and Express (4000) listen on loopback. Runtime credentials are not build arguments. The service's health route checks its process listener; a healthy status alone does not prove database access.

For later secret changes, use the Environment settings in the Render Dashboard and redeploy the existing build. Variables marked `sync: false` prompt only at initial Blueprint creation. Keep the same JWT secret unless intentionally revoking all existing authentication tokens. A second unrelated frontend hostname is incompatible with the current socket cookie contract.

## Local verification

```bash
npm run check
npm run test:system
npm run test:deploy
```

`test:deploy` builds the combined image and uses the permanent Chromium suite through the proxy, with the application capped at 512 MB and a disposable local MySQL database. It prints the container's cgroup peak memory at the end and always attempts to remove its own containers/volume. Local HTTP uses a non-Secure test cookie; live HTTPS/Secure-cookie and external MySQL/TLS checks are separate.

The combined image runs as an unprivileged user. Its supervisor stops the remaining processes if one fails, and forwards shutdown signals with a bounded fallback. nginx disables response buffering for streamed Server Components. No application pages or API responses are added to the PWA cache.

Record actual results in the stage status/handoff: remote migrations over verified TLS, HTTPS registration/login and cookie flags, two-tab sockets/reconnect, charts/graph/map configuration, CSV, PWA/offline, memory under demo load, persistence across redeploy, and a database export/restore rehearsal against an isolated target. Do not mark these checked from local HTTP tests alone.
