# Stage plan

Every stage lives in its own `stage/N-name` branch cut from `main`. The details of a stage are discussed before it starts; the branch is merged into `main` (`--no-ff`) only after an explicit OK.

During stage 0 a set of ESLint rules was agreed (promises with type-aware checks on the client and the server, import order and type imports through `simple-import-sort`, client layer boundaries, safety rules). Details are in [CODING_RULES.md](CODING_RULES.md#eslint-rules). New rules are added there and to the configs as the stages go on.

Stage 2 decisions (agreed): the scope is the shell, the lists and the visual part of the delete window on static data; Bootstrap 5 from SCSS plus global BEM next to the components; animations through React `<ViewTransition>` plus CSS; all five sidebar items, the three without a section open a `ComingSoon` page; the search field and the add and delete buttons are drawn but disabled until their stages; the chosen order and the type filter live in the address (`?order=2`, `?type=Monitors`); a desktop layout that adapts down to a phone.

Stage 2 additions (agreed later): a working live search in the top menu (`?q=`, orders and products), smooth reflow of rows through named view transitions, staggered rows, directional page transitions by sidebar order, a faded dialog backdrop and a panel that scrolls into view on narrow screens. Stage 3 follow-up: the real API needs `q` support on `GET /orders` and `GET /products` (SQL `LIKE` in the repositories), or the client keeps filtering.

Client architecture (agreed): feature structure `app/` → `features/<name>/{components,hooks,api,store}` → `shared/`, features talk to each other only through `index.ts` (details in [CODING_RULES.md](CODING_RULES.md#client-architecture-clientsrc)).

Server architecture (agreed): feature modules `modules/<name>` with routes → service → repository layers, domain errors instead of HTTP errors in services, dependencies wired by factories in `app.ts`, file names like `orders.service.ts` (details in [CODING_RULES.md](CODING_RULES.md#server-serversrc)).

Stage 1 decisions (agreed): Liquibase changelog in YAML; DB access through `mysql2` with hand-written SQL, no ORM; prices in a separate `product_prices` table, types in `product_types`; `ON DELETE CASCADE` for products and prices when an order is deleted; the REST API includes `POST /orders` and `POST /products` (validation by hand, a library may replace it in stage 5); integration tests on a separate `dzencode_test` database; the Workbench `.mwb` file is made by reverse engineering from a live database (steps in the README), the repository holds the dump `docs/db/schema.sql`.

Stage 3 decisions (agreed): Redux Toolkit with one slice per feature and `createAsyncThunk` over the existing `request` (no RTK Query); the address stays the source of truth for the open order, the type and the search; the search runs on the server (`q` on `GET /orders` and `GET /products`, SQL `LIKE`); the mocks and `data.ts` are deleted; the first load shows skeletons, a failure shows an error block with a retry button, and a list that reloads keeps its previous rows (dimmed). Data is loaded in the browser, server prefetch stays in stage 6. Add and delete buttons stay disabled until stage 5.

Stage 4 decisions (agreed): a session is an open browser tab (one socket connection), as the task says; the counter state lives in Redux (`features/sessions`: connection status and the last count) and is fed by a socket channel in `api/`; the top menu shows a dash while there is no connection and the number returns by itself after a reconnect; the registry is in the memory of one server process and this limit is written into `docs/API.md`; Socket.io runs on the same HTTP server and origin as the REST API; the server side is tested over real sockets. The branch is cut from `stage/3-orders-products` because the Redux store comes from stage 3.

Stage 5 decisions (agreed): the add forms are separate pages (`/orders/new`, `/products/new?order=`), not windows; validation with `react-hook-form` and `zod` on the client, the server's hand-written checks stay the final judge; the product form has two fixed price fields (USD and UAH, UAH is the main one) and no photo upload; deletion of an order and of a product (new `DELETE /products/:id`) goes through a confirmation window; after a save the visitor lands on the panel of the order; other open tabs do not learn about changes at once (that is the event-driven stage 7).

Stage 6a decisions (agreed): inventory data is owned by the Next Data Cache; Server Components render orders/products, and Server Actions call the existing REST API for mutations. Redux owns sessions and confirmation UI. Reads use tags and a 60-second revalidation interval; mutations expire affected tags with `updateTag`, and deletions call `refresh`. URL search/filter/panel state and View Transitions stay. React Testing Library + jsdom covers DOM behavior and race conditions. Private `API_URL` points Next at the API inside Compose; public `NEXT_PUBLIC_API_URL` is only for health and sockets. See [ADR 0001](adr/0001-server-first-data.md).

Each part of stage 6 normally starts from `main` after the preceding part is reviewed and merged with the owner's explicit OK. The owner approved one exception for 6c: implement the independent server work from main in a separate worktree while 6b awaits review; complete client integration only after 6b is accepted. Uncommitted 6b work must not be silently copied or treated as accepted. Details of 6b–6d are discussed before implementation. GraphQL remains in stage 7 for aggregate reads in Groups; REST remains the CRUD API.

Stage 6c decisions (approved): one shared inventory for all authenticated users, without roles; registration with first/last name, normalized unique email, password and confirmation, with automatic login. Salted scrypt passwords; generic login failure and process-local throttling. JWTs have no automatic expiry or refresh tokens; MySQL `auth_sessions` makes them revocable. Next Server Actions own the long-lived HttpOnly/SameSite=Lax cookie (Secure under HTTPS) and forward bearer authorization to Express. Validate sessions before cached inventory hits and isolate cache keys without storing bearer tokens. Protect REST, pages and actions; synchronize auth across tabs, scope drafts by user, reset transient state and guard late results. Authenticate sockets with the HttpOnly cookie, validate Origin and disconnect the revoked session's tabs. Users shows the current-user card and public participant names/registration dates. See [ADR 0002](adr/0002-authentication.md) and [implementation status](AUTH_IMPLEMENTATION.md) for the complete contract and owner review checklist.

Stage 6b decisions (agreed): English is the default, with an EN/RU switch in the top menu and a one-year HttpOnly locale cookie; no browser-language detection or URL prefix. Dictionaries live next to their page/component and load only for the selected language. Client providers receive messages only for their mounted scope; server-only messages stay on the server. Feature public entries remain index.ts: exported dictionary loaders are request-independent, and server wrappers read the locale. Forms use localStorage drafts with a seven-day lifetime since the last edit, a clear button and cleanup after a successful save. The data itself is not translated. JWT cookies remain in stage 6c.

Stage 6b was accepted into main at c6170a3. The owner authorized integrating that base and completing the remaining stage 6c client work. After implementation, verification and independent review fixes, the owner approved committing stage 6c and merging it into main.

Stage 6d was prepared independently from stage 6a in its own worktree with the owner's approval. After 6b/6c were merged into main (`232b07f`), the owner authorized completing the combined integration in `stage/6d-charts-maps`. Warehouses are a read-only seeded reference; each order has zero or one warehouse and its products inherit that location. Groups reports server-aggregated inventory counts/value with explicit UAH/USD selection, missing-price coverage, exact tables and deferred selective Chart.js bars. Direct Leaflet and CSS load only after Show map. The owner selected a configurable HTTPS tile template with no provider by default. Full requirements and verification are in [STAGE_6D_PLAN.md](STAGE_6D_PLAN.md) and [STAGE_6D_STATUS.md](STAGE_6D_STATUS.md). After the verification recorded there, the owner approved committing stage 6d and merging it into main.

Stage 7 decisions (agreed): four branches 7a-7d, each from `main` after the previous one is reviewed. REST stays for CRUD, authentication, sessions and the warehouse list (the base task requires REST); GraphQL (graphql-yoga) is read-only and analytical, and the REST statistics endpoint is removed in 7a. The graph of choice is the warehouse - order - product-type relations graph from GraphQL, drawn lazily with Cytoscape.js. Event-driven architecture (7b) is a typed in-process event bus delivered through the existing Socket.io, without Redis. The Web Worker (7c) builds the CSV export of the current lists; the PWA caches static assets and an offline page, never API data or authenticated pages. 7d adds Playwright as the permanent end-to-end suite. The 7a plan and review checklist are in [STAGE_7A_PLAN.md](STAGE_7A_PLAN.md) and [ADR 0004](adr/0004-graphql-and-relations-graph.md).

Stage 7c decisions (agreed): CSV export on Orders and Products (current search and filter, the delimiter follows the language, UTF-8 with BOM, the file built in a Web Worker); a minimal PWA (manifest, a hand-written service worker for production and a secure context that caches only hashed static files and an offline page, quiet updates); icons generated from the current logo; front-end optimization by measurement with cheap, safe fixes only (Bootstrap and the shared SCSS untouched). The plan and review checklist are in [STAGE_7C_PLAN.md](STAGE_7C_PLAN.md), the results in [STAGE_7C_STATUS.md](STAGE_7C_STATUS.md) and [ADR 0006](adr/0006-csv-worker-pwa-and-lean-first-load.md).
