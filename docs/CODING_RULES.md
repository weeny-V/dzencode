# Правила разработки

Правила, которые нужно соблюдать, чтобы не повторять уже найденные ошибки. Новое правило добавляем сюда, когда замечание повторилось или стоило времени.

## Процесс

1. Работаем по этапам из [PLAN.md](PLAN.md), каждый в ветке `stage/N-name`.
2. Перед этапом обсуждаем детали с владельцем проекта и только потом реализуем.
3. Ничего не коммитим и не вливаем в `main` без явного ОК.
4. Не пишем «работает», пока не проверили. В отчёте отдельно называем то, что не проверено (например, Docker).
5. Запущенные для проверки dev-серверы и процессы останавливаем после проверки.
6. Документацию и ответы ведём на русском. **Весь код на английском:** идентификаторы, комментарии, имена файлов, сообщения логов и ошибок. Исключение: тексты интерфейса в компонентах пока могут быть на русском.

## Архитектура клиента (`client/src`)

Код разложен по feature-модулям. Слои идут строго сверху вниз: `app` → `features` → `shared`.

```
src/
  app/                       # маршруты Next.js: только собирают фичи
  features/<name>/           # одна предметная область (orders, products, api-status…)
    components/<Component>/  # index.tsx (+ useX.ts хука этого компонента)
    hooks/                   # хуки, общие для нескольких компонентов фичи
    api/                     # запросы фичи
    store/                   # Redux slice фичи (с этапа 3)
    index.ts                 # публичный интерфейс фичи
  shared/                    # то, что нужно нескольким фичам
    api/ config/ hooks/ ui/  # HTTP-клиент, env, общие хуки, общие UI-блоки
```

| Слой        | Что внутри                                          | Чего там быть не должно                    |
| ----------- | --------------------------------------------------- | ------------------------------------------ |
| `app/`      | Маршруты, layout: только собирают фичи              | Логика и запросы                           |
| `features/` | Компоненты, хуки, запросы и store одной фичи        | Импорты из `app/`, внутренности других фич |
| `shared/`   | Универсальные куски без знания о предметной области | Импорты из `features/` и `app/`            |

Внутри фичи слои идут так же сверху вниз: `components` → `hooks` → `api`; в `shared/`: `hooks` → `api` → `config`.

1. **Компонент не работает с промисами.** `fetch` и `await` живут в `api/` и хуках; компонент получает готовый результат.
2. **Где лежит хук.** Хук нужен одному компоненту: рядом с ним, `components/X/useX.ts`. Нескольким компонентам одной фичи: `features/<name>/hooks/`. Нескольким фичам: `shared/hooks/`.
3. **Фича к фиче обращается только через `index.ts`** (`@/features/orders`). Внутри одной фичи импортируем относительными путями, между слоями приложения через алиас `@/`. Публичным делаем только то, что нужно снаружи (обычно компонент верхнего уровня).
4. **Container / Presentational.** Контейнер берёт данные из хука и передаёт вниз без собственной разметки. View получает всё через props, не ходит в сеть, не читает env и не знает о store (допустимо только локальное UI-состояние).
5. **Не дробим мелкие компоненты.** Пока блок маленький, контейнер и View лежат в одном `components/X/index.tsx` (View не экспортируется). Разносим по `XContainer.tsx` и `XView.tsx`, только когда файл заметно вырос или View нужен отдельно.
6. View может импортировать из слоёв ниже только **типы** (`import type`).
7. Переменные окружения читаются только в `shared/config/env.ts`; конфигурацию не кладём в `lib/`.
8. Адреса, порты и URL не хардкодим в компонентах, берём из `shared/config/`.
9. Новая фича это новая папка `features/<name>` по шаблону выше; слои, которых ей пока не нужно, не создаём заранее.
10. Правила слоёв проверяет линтер ([ESLint-правила](#eslint-правила)): `shared/` не импортирует `features/` и `app/`, глубокие импорты соседней фичи и `fetch` вне `api/` запрещены. Ограничение линтера: относительный путь в соседнюю фичу (`../../../orders/...`) он не ловит, так что ходим только через алиас.

## Асинхронный код

1. Не строим цепочки `.then().catch()`: используем `async/await` с `try/catch`.
2. Эффект React не может быть `async`, поэтому внутри него объявляем `async`-функцию и вызываем её как `void run()`.
3. Запрос, который можно прервать, получает `AbortSignal`; `AbortError` не считаем ошибкой.
4. **`try/catch` для запросов живёт в одном месте:** общий хук `useRequest(fn, { onSuccess, onError })` в `src/shared/hooks/`. Он ведёт состояние `loading / success / error`, прерывает запрос при размонтировании и игнорирует `AbortError`. Хуки и компоненты берут из него готовый статус или колбэки и сами `try/catch` не пишут. Слой `api/` колбэков не знает: он возвращает промисы и бросает `ApiError`.

## Сервер (`server/src`)

Код разложен по feature-модулям. Корень `src/` содержит только точки входа (`index.ts`, `app.ts`, `config.ts`), `modules/` отвечает за предметную область, `shared/` за то, что нужно всем.

```
src/
  index.ts  app.ts  config.ts       # запуск, composition root, env
  shared/
    errors.ts                        # доменные ошибки (NotFoundError, ValidationError)
    validation.ts                    # примитивы проверки ввода
    db/                              # пул, транзакции, ошибки драйвера
    http/                            # обработчик ошибок
    testing/                         # хелперы интеграционных тестов (не попадают в сборку)
  modules/<name>/
    <name>.routes.ts                 # HTTP: разбор запроса, вызов сервиса
    <name>.service.ts                # бизнес-правила, доменные ошибки
    <name>.repository.ts             # только SQL
    <name>.schemas.ts                # проверка входных данных
    <name>.types.ts
    index.ts                         # публичный интерфейс модуля
```

1. **Цепочка слоёв:** routes → service → repository → БД. Роут не знает про SQL, репозиторий не знает про HTTP и бизнес-правила, сервис не импортирует `express`.
2. **Ошибки доменные.** Сервис бросает `NotFoundError` / `ValidationError`, статус HTTP определяет единственный обработчик `shared/http/errorHandler.ts`. Репозиторий переводит ошибки драйвера в типизированные (например, `ForeignKeyViolationError`), а сервис решает, что они значат. Всё остальное уходит в 500 без деталей.
3. **Зависимости собираются фабриками** (`createXService({ repository, ... })`) в одном месте: `app.ts` (composition root). Глобальных синглтонов и DI-контейнера нет, в тестах зависимости подменяются.
4. **Модуль обращается к другому только через его `index.ts`** и только к сервису (`Pick<XService, ...>` с нужными методами). Граф зависимостей без циклов: `orders` → `products` → `product-types` (циклы импортов запрещает `import/no-cycle`). **Таблицы другого модуля репозиторий не изменяет и не содержит их бизнес-логики.** Для чтения допустим `JOIN` по ключу ради отображаемых полей (например, `products` показывает название типа и прихода): иначе каждый список превратился бы в N запросов к соседним сервисам. Всё, что считается или решается по данным другого модуля (счётчики, суммы, проверки правил), берём у его сервиса.
5. Границы проверяет линтер: `mysql2` только в `*.repository.ts` и `shared/db`, `express` только в `*.routes.ts`, `app.ts` и `shared/http`, глубокие импорты соседнего модуля запрещены.
6. Новая сущность это новая папка `modules/<name>` по шаблону выше и одна строка в `app.ts`.
7. Переменные окружения читаются только в `config.ts`.
8. В лог пишем адрес, к которому сервер реально привязан (`formatAddress(server.address())`), а не зашитый `localhost`.
9. Каждый промис ожидаем или явно помечаем `void` (type-aware ESLint это проверяет: `no-floating-promises`, `no-misused-promises`).
10. Логи пишем через `console.info` / `console.warn` / `console.error`; `console.log` запрещён линтером.

## База данных

1. **Схема меняется только через Liquibase** (`db/changelog`, YAML). Применённые changeSet'ы не редактируем: любое изменение это новый changeSet. Таблицы руками не правим.
2. **SQL пишется только в `*.repository.ts`.** Только параметризованные запросы (`?`): строки собираем из фиксированных фрагментов, значения из запроса в SQL текстом не вставляем.
3. **Несколько связанных записей пишем в транзакции** (`withTransaction` из `shared/db/transaction.ts`): продукт и его цены.
4. **Целостность проверяет база, если это можно выразить в схеме.** Существование родителя (например, прихода) гарантирует внешний ключ, а не предварительный SELECT: так нет гонки между проверкой и вставкой. Период гарантии проверяет `CHECK`. Правила, которые MySQL выразить не может (ровно одна цена по умолчанию), проверяет API.
5. **Входные данные проверяются по границам колонок,** иначе MySQL отвечает ошибкой, а клиент получает 500: `INT` (до 2 147 483 647), `DECIMAL(12,2)` (до 9 999 999 999,99 и не больше двух знаков), `VARCHAR(n)` считается в символах, `TEXT` в байтах (65 535), `DATETIME` с годами 1000–9999.
6. **В БД `snake_case`, в API `camelCase`.** Преобразование делает репозиторий; форма ответа повторяет `app.js`.
7. **Даты** хранятся как `DATETIME` в UTC с точностью до секунды и отдаются ISO-строками (пул создаётся с `timezone: 'Z'`). На вход принимаем только ISO 8601; дата без часового пояса считается UTC, миллисекунды отбрасываются.
8. **Регистр.** Колонки сравниваются без учёта регистра (`utf8mb4_0900_ai_ci`): фильтр `?type=monitors` находит `Monitors`. Коды валют приводятся к верхнему регистру при вводе.

## Тесты сервера

1. **Три вида тестов рядом с модулем:** юнит сервиса с подменённым репозиторием (`*.service.test.ts`), проверка входных данных (`*.schemas.test.ts`) и интеграционный по HTTP на реальной БД (`*.api.test.ts`).
2. Интеграционные тесты идут на БД `<DB_NAME>_test` (нужен `npm run db:up`), данные пересоздаются перед каждым тестом через `shared/testing/database.ts`. Не пишем тесты, зависящие от демо-данных сида.
3. Файлы тестов выполняются по очереди (`fileParallelism: false` в `server/vitest.config.mjs`), потому что делят одну тестовую БД. Тот же конфиг подгружает `server/.env`, как `npm run dev`.
4. Тест ошибок проверяет статус и тело ответа, а для «ничего не сохранено» ещё и количество строк в таблицах. Ошибки 500 тестируем на подменённом пуле (без БД).

## Окружение

1. У каждого модуля свой пример: `server/.env.example` (загружается Node через `--env-file-if-exists`), `client/.env.example` (копируем в `client/.env.local`).
2. Корневой `.env.example` нужен только для `docker compose`, локальный `npm run dev` его не читает.
3. Требуется Node.js ≥ 22.9 (флаг `--env-file-if-exists`).

## Инструменты

1. **Форматирование — только Prettier** (кавычки, `;`, ширина строки, запятые). ESLint отвечает за качество кода и не дублирует стилистические правила: `eslint-config-prettier` их намеренно отключает, иначе правила конфликтуют.
2. Общие правила ESLint лежат в `eslint.shared.mjs` и подключаются последними в конфиге каждого пакета.
3. В тестах не оставляем `any`: ответы `supertest` и подобное приводим к типу.
4. Перед выбором версии пакета проверяем peer-зависимости (например, `typescript-eslint` требует TypeScript `<6.1`).
5. Не применяем `npm audit fix --force` вслепую: сначала смотрим, существует ли исправленная версия. Для production-зависимостей используем `npm run audit:prod`.
6. Скрипты с postinstall разрешаем явно через `npm install-scripts approve`.
7. Многострочные тексты в файлы пишем инструментом записи файлов, а не через шелл-heredoc: шелл ломает обратные кавычки.

## ESLint-правила

Правила, общие для клиента и сервера, лежат в `eslint.shared.mjs`; специфика слоёв клиента и границы модулей сервера в конфигах пакетов. Плагины `eslint-plugin-simple-import-sort` и `eslint-plugin-import` стоят в корне и работают в обоих пакетах. Проверки на клиенте и сервере одинаково type-aware (`recommendedTypeChecked`).

| Группа    | Правила                                                                                                                                            | Что даёт                                                                                                                              |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Промисы   | `no-floating-promises`, `no-misused-promises` (клиент и сервер); `no-restricted-syntax` на `.then` / `.catch` / `.finally`                         | Нет висящих промисов и цепочек, как в разделе «Асинхронный код»                                                                       |
| Импорты   | `simple-import-sort/imports` и `/exports`, `import/no-duplicates`, `import/no-cycle`, `@typescript-eslint/consistent-type-imports` (inline `type`) | Единый порядок импортов (пакеты, затем `@/`, затем относительные), без дублей и циклов, типы через `type`; сортировка чинится `--fix` |
| Слои      | `@typescript-eslint/no-restricted-imports` по папкам `src/`; `no-restricted-properties` на `process.env`; `no-restricted-globals` на `fetch`       | Слои и фичи не нарушают границы; env читается только в `shared/config/env.ts` (клиент) и `config.ts` (сервер); сеть в `api/`          |
| Страховка | `eqeqeq`, `no-console` (разрешены `info`, `warn`, `error`), `switch-exhaustiveness-check`                                                          | Строгое сравнение, нет забытых `console.log`, `switch` по union покрывает все варианты                                                |

Сознательно не включены: `@typescript-eslint/no-non-null-assertion` (оставляем `!` на усмотрение) и стилистические правила React (`self-closing-comp`, `jsx-boolean-value`, `function-component-definition`): форматирование и стиль остаются за Prettier.

Исключения из правил слоёв клиента: хук рядом с компонентом (`components/X/useX.ts`) может импортировать `api/`, потому что он и есть место для запросов этого компонента; из самого компонента (не хука) в `api/` можно импортировать только типы (`import type`); `shared/config` компонентам доступен. Если правило мешает, а не помогает, обсуждаем его и меняем в конфиге, а не отключаем комментарием `eslint-disable` на месте.
