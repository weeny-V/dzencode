# Правила разработки

Правила, которые нужно соблюдать, чтобы не повторять уже найденные ошибки. Новое правило добавляем сюда, когда замечание повторилось или стоило времени.

## Процесс

1. Работаем по этапам из [PLAN.md](PLAN.md), каждый в ветке `stage/N-name`.
2. Перед этапом обсуждаем детали с владельцем проекта и только потом реализуем.
3. Ничего не коммитим и не вливаем в `main` без явного ОК.
4. Не пишем «работает», пока не проверили. В отчёте отдельно называем то, что не проверено (например, Docker).
5. Запущенные для проверки dev-серверы и процессы останавливаем после проверки.
6. Документацию и ответы ведём на русском. **Весь код на английском:** идентификаторы, комментарии, имена файлов, сообщения логов и ошибок. Исключение: тексты интерфейса в компонентах пока могут быть на русском.

## Архитектура клиента (`client/src`)

Зависимости идут строго сверху вниз: `app` → `components` → `hooks` → `api` → `config`.

| Папка         | Что внутри                                      | Чего там быть не должно          |
| ------------- | ----------------------------------------------- | -------------------------------- |
| `config/`     | Чтение `process.env` (единственное место)       | Бизнес-логика, запросы           |
| `api/`        | HTTP-клиент и функции запросов, без React       | Хуки, JSX, состояние компонентов |
| `hooks/`      | Только **общие** хуки (нужны нескольким блокам) | Разметка, хуки одного компонента |
| `components/` | UI-блоки; хук одного блока лежит рядом с ним    | `fetch`, промисы, `process.env`  |
| `app/`        | Маршруты Next.js: только собирают компоненты    | Логика и запросы                 |

1. **Компонент не работает с промисами.** `fetch` и `await` живут в `api/` и хуках; компонент получает готовый результат.
2. **Где лежит хук.** Хук нужен нескольким компонентам: `src/hooks/useX.ts`. Хук нужен одному компоненту: рядом с ним, `components/X/useX.ts`.
3. **Container / Presentational.** Контейнер берёт данные из хука и передаёт вниз без собственной разметки. View получает всё через props, не ходит в сеть, не читает env и не знает о store (допустимо только локальное UI-состояние).
4. **Не дробим мелкие компоненты.** Пока блок маленький, контейнер и View лежат в одном `components/X/index.tsx` (View не экспортируется). Разносим по `XContainer.tsx` и `XView.tsx`, только когда файл заметно вырос или View нужен отдельно.
5. View может импортировать из слоёв ниже только **типы** (`import type`).
6. Переменные окружения читаются только в `config/env.ts`; конфигурацию не кладём в `lib/`.
7. Адреса, порты и URL не хардкодим в компонентах, берём из `config/`.
8. Правила слоёв проверяет линтер ([ESLint-правила](#eslint-правила)): между слоями импортируем через алиас `@/`, обращение вверх по цепочке и `fetch` вне `api/` запрещены.

## Асинхронный код

1. Не строим цепочки `.then().catch()`: используем `async/await` с `try/catch`.
2. Эффект React не может быть `async`, поэтому внутри него объявляем `async`-функцию и вызываем её как `void run()`.
3. Запрос, который можно прервать, получает `AbortSignal`; `AbortError` не считаем ошибкой.
4. **`try/catch` для запросов живёт в одном месте:** общий хук `useRequest(fn, { onSuccess, onError })` в `src/hooks/`. Он ведёт состояние `loading / success / error`, прерывает запрос при размонтировании и игнорирует `AbortError`. Хуки и компоненты берут из него готовый статус или колбэки и сами `try/catch` не пишут. Слой `api/` колбэков не знает: он возвращает промисы и бросает `ApiError`.

## Сервер (`server/src`)

1. Переменные окружения читаются только в `config.ts`.
2. В лог пишем адрес, к которому сервер реально привязан (`formatAddress(server.address())`), а не зашитый `localhost`.
3. Каждый промис ожидаем или явно помечаем `void` (type-aware ESLint это проверяет: `no-floating-promises`, `no-misused-promises`).
4. Логи пишем через `console.info` / `console.warn` / `console.error`; `console.log` запрещён линтером.

## Окружение

1. У каждого модуля свой пример: `server/.env.example` (загружается Node через `--env-file-if-exists`), `client/.env.example` (копируем в `client/.env.local`).
2. Корневой `.env.example` нужен только для `docker compose`, локальный `npm run dev` его не читает.
3. Требуется Node.js ≥ 22.9 (флаг `--env-file-if-exists`).

## Инструменты

1. **Форматирование — только Prettier** (кавычки, `;`, ширина строки, запятые). ESLint отвечает за качество кода и не дублирует стилистические правила: `eslint-config-prettier` их намеренно отключает, иначе правила конфликтуют.
2. Общие правила ESLint лежат в `eslint.shared.mjs` и подключаются последними в конфиге каждого пакета.
3. В тестах не оставляем `any`: ответы `supertest` и подобное приводим к типу.
4. Перед выбором версии пакета проверяем peer-зависимости (например, `typescript-eslint` требует TypeScript `<6.1`).
5. Не применяем `npm audit fix --force` вслепую: сначала смотрим, существует ли исправленная версия. Для production-зависимостей используем `npm run audit:prod`.
6. Скрипты с postinstall разрешаем явно через `npm install-scripts approve`.

## ESLint-правила

Правила, общие для клиента и сервера, лежат в `eslint.shared.mjs`; специфика слоёв клиента и `process.env` сервера, в конфигах пакетов. Плагины `eslint-plugin-simple-import-sort` и `eslint-plugin-import` стоят в корне и работают в обоих пакетах. Проверки на клиенте и сервере теперь одинаково type-aware (`recommendedTypeChecked`).

| Группа    | Правила                                                                                                                                      | Что даёт                                                                                                           |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Промисы   | `no-floating-promises`, `no-misused-promises` (клиент и сервер); `no-restricted-syntax` на `.then` / `.catch` / `.finally`                   | Нет висящих промисов и цепочек, как в разделе «Асинхронный код»                                                    |
| Импорты   | `simple-import-sort/imports` и `/exports`, `import/no-duplicates`, `@typescript-eslint/consistent-type-imports` (inline `type`)              | Единый порядок импортов (пакеты, затем `@/`, затем относительные), без дублей, типы через `type`; чинится `--fix`  |
| Слои      | `@typescript-eslint/no-restricted-imports` по папкам `src/`; `no-restricted-properties` на `process.env`; `no-restricted-globals` на `fetch` | Зависимости идут сверху вниз; env читается только в `config/env.ts` (клиент) и `config.ts` (сервер); сеть в `api/` |
| Страховка | `eqeqeq`, `no-console` (разрешены `info`, `warn`, `error`), `switch-exhaustiveness-check`                                                    | Строгое сравнение, нет забытых `console.log`, `switch` по union покрывает все варианты                             |

Сознательно не включены: `@typescript-eslint/no-non-null-assertion` (оставляем `!` на усмотрение) и стилистические правила React (`self-closing-comp`, `jsx-boolean-value`, `function-component-definition`): форматирование и стиль остаются за Prettier.

Исключения из правил слоёв: хук рядом с компонентом (`components/X/useX.ts`) может импортировать `api/`, потому что он и есть место для запросов этого компонента; из самого компонента (не хука) в `api/` можно импортировать только типы (`import type`). Если правило мешает, а не помогает, обсуждаем его и меняем в конфиге, а не отключаем комментарием `eslint-disable` на месте.
